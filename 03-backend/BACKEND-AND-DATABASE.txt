MANABI PREP - BACKEND & DATABASE REFERENCE
==========================================
Folder: 03-backend/
Last reviewed: 2026-11-26


1. WHAT THE BACKEND IS
----------------------
A Python FastAPI server that runs timed mock exams (JFT-Basic and JLPT N5-N1),
grades them with each exam's real scoring rules, and remembers your mistakes.

- Framework : FastAPI + Uvicorn
- Database  : SQLAlchemy 2.0 ORM, migrations with Alembic
- DB engine : SQLite file by default (manabi_prep.db)
              PostgreSQL when DATABASE_URL points to Postgres (psycopg 3 driver)
- Users     : single user only ("student-default"), no login

The web app (02-web-app) calls this API for mock exams. If the API cannot be
reached, the web app falls back to running mock exams in the browser and saves
them in localStorage. The live Vercel site currently always uses that fallback,
because the backend is not deployed yet.

3. HOW TO RUN IT
----------------
Quick local run (SQLite, no setup):
    cd 03-backend
    pip install -r requirements.txt
    uvicorn app.main:app --reload --port 8000
    -> API docs: http://127.0.0.1:8000/docs
    -> Health:   http://127.0.0.1:8000/health

With Postgres via Docker:
    cd 03-backend
    docker compose up --build
    (runs: alembic upgrade head -> seeder -> uvicorn on port 8000)

Run tests:
    cd 03-backend
    python -m pytest -q

The web app finds the API through NEXT_PUBLIC_API_BASE_URL
(default http://127.0.0.1:8000).

6. API ENDPOINTS
----------------
GET  /health                                    -> {"status": "ok"}

GET  /api/v1/exams                              Catalog of all 6 exams with
                                                available question counts per section
GET  /api/v1/exams/{exam_code}                  One exam

GET  /api/v1/attempts                           Last 30 attempts (history)
POST /api/v1/attempts                           Start an attempt
     body: {exam_code, mode: "full"|"section", section?, question_limit?}
GET  /api/v1/attempts/{id}                      Current state + remaining time
PUT  /api/v1/attempts/{id}/answers/{question_id}
     body: {selected_option_id, marked_for_review, time_spent_sec}
POST /api/v1/attempts/{id}/submit               Grade it (safe to call twice)
     body (optional): {total_time_sec}
GET  /api/v1/attempts/{id}/results              Graded result with full review

GET  /api/v1/mistakes?status=active&exam_code=N2   Mistake bank list
GET  /api/v1/mistakes/progress                  Per-section running accuracy

Correct answers are never sent while an attempt is in progress; they appear only
in the results after submit.


7. HOW A MOCK EXAM WORKS
------------------------
Start:
  - Full mode: takes each section's question quota from the blueprint (random).
    With question_limit, the limit is split across sections in proportion
    to the blueprint, so every section is still included.
  - Section mode: random questions from one section only.
  - The time limit shrinks in proportion if fewer questions are available
    (minimum 5 min full / 3 min section).
  - Choice order is shuffled and saved in question_snapshot_json.

Answer:
  - Each answer is saved straight away (upsert), so a refresh does not lose it.
  - Answers cannot change after submit.

Submit / scoring:
  - JFT-Basic (jft_250): score = correct / total x 250. Pass at 200.
    No per-section minimum.
  - JLPT (jlpt_180): score = correct / total x 180. Must reach the overall pass
    mark AND each section must reach its minimum (19/60, or 10/30 for N5 reading).
  - Section mode: pass mark scaled down from the full exam ratio.
  - Weak sections = below 70% accuracy (or the lowest section if all are 70%+).
  - Weak topics = the 5 most-missed topic tags.

Mistake bank rules:
  - Wrong answer -> wrong_count + 1, consecutive_correct reset to 0, status "active".
  - Correct answer on a question already in the bank -> consecutive_correct + 1.
  - 2 correct in a row -> status "resolved".

On every server start (main.py lifespan):
  1. Create any missing tables.
  2. Make sure the default user exists.
  3. Insert/update the 6 exam blueprints.
  4. Insert any new questions from questions.json (existing ids are skipped,
     so edited questions are NOT updated - only new ones are added).


8. WHAT WORKS AND WHAT IS MISSING
---------------------------------
Works:
  - Full mock exam flow, scoring, mistake bank, per-section progress.
  - 4 engine tests pass.

Missing / known limits:
  - Not deployed anywhere; the live site uses the in-browser fallback.
  - No login. Every request acts as "student-default". Anyone who knows the API
    URL could read or add data once it is public.
  - Practice-mode progress, daily activity, tasks and settings are NOT stored
    here; they live only in the browser's localStorage.
  - ai_conversations / ai_messages tables exist but nothing uses them.
  - Seeder does not update questions that were edited in questions.json.
  - __pycache__ files and manabi_prep.db are tracked in git; they should be
    in .gitignore instead.


9. NOTES FOR DEPLOYING ON VERCEL
--------------------------------
Vercel can run this FastAPI app as Python serverless functions, but:

  - SQLite will not work there. Vercel's disk is temporary and wiped, so data
    would be lost. Use hosted Postgres instead: Neon (free tier) added from
    Vercel -> Storage. It sets DATABASE_URL; the URL scheme must be
    postgresql+psycopg:// for this code (Neon gives postgres://...).
  - The seeder reads ../02-web-app/data/questions.json, which is outside
    03-backend. A Vercel project rooted at 03-backend cannot see that file, so
    the questions need to be copied in at build time or loaded once from a
    local machine.
  - Running create_all + seeding on every cold start slows the first request.
    Better: run "alembic upgrade head" and the seeder once, from your machine,
    against the Neon database.
  - CORS_ORIGINS must include https://manabi-ai-eta.vercel.app.
  - The web app needs NEXT_PUBLIC_API_BASE_URL set to the backend's Vercel URL,
    then a redeploy.
  - Before it is public, add a simple shared secret (API key header) so random
    visitors cannot write to the database.
